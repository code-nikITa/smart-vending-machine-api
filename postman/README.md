# Postman-коллекция

Коллекция покрывает все эндпоинты API, все документированные ветки ошибок (400/402/404/409) и полный сценарий покупки от начала до конца. Каждый запрос содержит автоматические тесты (`pm.test`), проверяющие и HTTP-статус, и форму/содержимое тела ответа.

## Файлы

| Файл | Назначение |
|---|---|
| `smart-vending-machine-api.postman_collection.json` | Сама коллекция: 9 папок, 24 запроса |
| `smart-vending-machine-api.postman_environment.json` | Environment с переменной `baseUrl` (по умолчанию `http://localhost:3000`) |
| `generate-collection.js` | Скрипт, которым коллекция сгенерирована. Коллекция — сгенерированный артефакт, а не файл для ручного редактирования: правки вносятся в скрипт, затем `node postman/generate-collection.js` пересобирает JSON |

## Структура коллекции

1. **Info** — health-check корневого эндпоинта
2. **Machine State** — `GET /machine`
3. **Restock** — создание/замена слота, включая валидационные ошибки (400)
4. **Insert Coins** — пополнение кредита, включая 400 на некорректную сумму
5. **Purchase Flow (Happy Path)** — последовательный сценарий: restock → insert → select → проверка состояния. Тесты сравнивают **дельты** (изменение revenue/credit/stock), а не абсолютные значения, поэтому сценарий надёжно проходит при повторных запусках на одном и том же сервере без перезапуска
6. **Purchase Errors** — 400/402/404/409 при покупке
7. **Maintenance** — `POST /machine/maintain`
8. **Error Handling (Generic)** — неизвестный роут (404), невалидный JSON в теле запроса (400)
9. **Broken Machine State** — документационная папка. У API намеренно нет debug-эндпоинта для принудительной поломки (это не предусмотрено спецификацией), поэтому реальный переход в `broken` происходит только после ~27 минут работы сервера (температура растёт на 3 каждую минуту от начальных 20 до >100). Папка объясняет это и не подделывает поведение, которого нет в API

## Способ 1 — через Postman (GUI)

1. Import → выбрать оба JSON-файла (коллекцию и environment)
2. Выбрать environment "Vending Machine - Local" в выпадающем списке справа сверху
3. Запустить сервер: `npm start`
4. Открыть коллекцию → Run collection, либо выполнять запросы по очереди вручную (важно соблюдать порядок внутри папок, особенно в "Purchase Flow")

## Способ 2 — через Newman (CLI, headless)

Сервер должен быть уже запущен в отдельном терминале:

```bash
npm start
```

В другом терминале:

```bash
npm run test:api
```

## Способ 3 — полностью автоматически (сервер стартует и гасится сам)

```bash
npm run test:api:ci
```

Эта команда сама поднимает сервер, дожидается его готовности (опрашивает `GET /machine`), прогоняет коллекцию и корректно завершает процесс сервера — независимо от результата тестов. Именно эта команда используется в GitHub Actions (job `api-tests` в `.github/workflows/test.yml`).

## Регенерация коллекции после правок в API

Коллекция собирается программно, а не редактируется руками в JSON — это позволяет держать её в git по-человечески (осмысленный diff) и переиспользовать хелперы между запросами. Если добавляешь новый эндпоинт или меняешь существующий:

1. Отредактируй `postman/generate-collection.js`
2. Пересобери: `node postman/generate-collection.js`
3. Проверь вживую: `npm run test:api:ci`
